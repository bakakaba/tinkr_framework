# Tinkerer Framework

Rust framework for bootstrapping consistent API services: HTTP + gRPC on multiplexed
port, layered configuration, structured logging, and OpenTelemetry.

```text
:8080 (IPv4 + IPv6)
  │
  ├─ application/grpc*  ──►  tonic services
  └─ everything else    ──►  axum router (+ built-in /health)
```

## Features

| Feature | Default | What it provides                                                              |
| ------- | ------- | ----------------------------------------------------------------------------- |
| `grpc`  | yes     | Serving gRPC via `tonic`. Disable with `default-features = false`.            |
| `otel`  | yes     | OpenTelemetry export: traces, metrics, and logs over OTLP, plus request spans.|

HTTP/REST support (via `axum`) is the base.

## Quickstart

```rust,no_run
use demo::MyGreeter;                          // your service implementation
use demo::pb::greeter_server::GreeterServer;  // generated by tonic-build or buf
use tinkr_framework::{Server, routing::get};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Load .env + config and set up logging + telemetry. Call exactly once.
    tinkr_framework::init!()?;

    // Serves until ctrl-c / SIGTERM, then shuts down gracefully.
    Server::new()
        .route("/hello", get(|| async { "hello" }))
        .grpc_service(GreeterServer::new(MyGreeter))
        .serve()
        .await?;
    Ok(())
}
```

Both protocols answer on the same port:

```sh
curl http://127.0.0.1:8080/hello             # -> hello
curl http://127.0.0.1:8080/health            # -> {"service":"demo",...,"status":"ok"}
grpcurl -plaintext -d '{"name":"world"}' \
    127.0.0.1:8080 hello.Greeter/SayHello    # -> {"message":"Hello world!"}
```

See [`kitchen_sink.rs`](crates/demo/examples/kitchen_sink.rs) for a demo of
all `Server` customizations.

## Configuration

Define your settings as a struct; `init!` resolves every field at startup
and freezes the result:

```rust
use tinkr_framework::config::{self, Configurable};

#[derive(Debug, Configurable)]
struct AppConfig {
    /// Greeting returned by `GET /greeting`.
    #[config(env = "GREETING", default = "Hello!")]
    greeting: String,

    /// Database connection URL; redacted in the startup readout.
    #[config(env = "DATABASE_URL", secret)]
    database_url: Option<String>,
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = tinkr_framework::init!(AppConfig)?;
    println!("{}", config.greeting);

    // Anywhere else in the service:
    let config = config::get::<AppConfig>();
    Ok(())
}
```

Each field resolves independently:

```text
env var  ──unset──►  config file  ──missing──►  #[config(default)]
```

The config file is `config.toml` in the working directory by default. Deployments
point one build at per-environment configuration by mounting it wherever they like
and setting `CONFIG_FILE=/etc/config/config.toml`; applications take full control
instead with `init!(AppConfig, config_file = path)` (a path or a runtime
`Option` — `None` keeps the default resolution). An explicitly named file must
exist; only the default `config.toml` may be absent.

- Provide your config struct to `tinkr_framework::init!(AppConfig)`; read it
  anywhere with `config::get::<AppConfig>()`.
- Use `.sources()` to trace where each value is sourced from.
- Use `config::write_schema` to generate a JSON Schema, giving `config.toml`
  autocompletion and validation in editors.

Full tour: [`crates/demo/examples/config.rs`](crates/demo/examples/config.rs).

## Observability

Logs go to stdout — human-readable locally, JSON when deployed — and carry
trace IDs, so they correlate with traces.

Enable telemetry export (traces, metrics, and logs) by pointing the service
at an [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/):

```sh
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
```

Each signal can be disabled or routed individually:

| Signal  | Disable (`=none`)       | Route elsewhere                       |
| ------- | ----------------------- | ------------------------------------- |
| Traces  | `OTEL_TRACES_EXPORTER`  | `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`  |
| Metrics | `OTEL_METRICS_EXPORTER` | `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` |
| Logs    | `OTEL_LOGS_EXPORTER`    | `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`    |

These variables follow the [OpenTelemetry SDK environment variable
specification](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/#exporter-selection).
Set `OTEL_LOGS_EXPORTER=none` on platforms that already collect stdout
(Cloud Run, GKE) to keep logs single-sourced.

## gRPC services

- `grpc_service` takes the generated `XxxServer<T>` — from **tonic-build /
  tonic-prost-build** (`build.rs`) or **buf** (`buf generate`); both emit the
  same type, so registration is identical.
- `grpc_reflection` enables [server reflection](https://grpc.io/docs/guides/reflection/)
  (`v1` + `v1alpha`) so clients like `grpcurl` can discover services. Pass an
  encoded `FileDescriptorSet` — from `tonic_prost_build`'s
  `file_descriptor_set_path` or buf's `file_descriptor_set` option (see
  `crates/demo/buf.gen.yaml`).

## Demo

The `demo` crate (`crates/demo`, not published) is the complete reference
setup: a buf-generated gRPC `Greeter`, HTTP routes, and layered config — all
on one port.

```sh
# Minimal configuration to get started
cargo run -p demo --example quickstart

# Every optional knob: router merging, shutdown hook, multiple binds, ...
cargo run -p demo --example kitchen_sink

# Layered configuration: config.toml, env overrides, provenance, schema
cargo run -p demo --example config    # run from crates/demo

# A consumer-prescribed deployment-environment enum
ENV=staging cargo run -p demo --example custom_env

# REST + gRPC telemetry flowing to the local LGTM stack
just up         # start Grafana/Tempo/Loki/Prometheus (http://localhost:3000)
just dev otel   # self-driving traffic; explore traces, logs, and metrics
just down       # stop the stack (ephemeral storage: this resets it)
```
